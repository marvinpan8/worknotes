## [介绍](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#introduction)

尽管并非所有插件都需要它，但您的插件可能需要在数据库中存储比其配置更多的信息。在这种情况下，Kong在其主要数据存储之上为您提供了一个抽象，使您可以存储自定义实体。

如[上一章所述](https://docs.konghq.com/1.3.x/plugin-development/access-the-datastore/)，Kong通过我们称为“ DAO”的类与模型层进行交互，并且可以在单例中被称为“ DAO工厂”。本章将说明如何为您自己的实体提供抽象。

## [模组](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#modules)

```
kong.plugins.<plugin_name>.daos
kong.plugins.<plugin_name>.migrations.init
kong.plugins.<plugin_name>.migrations.000_base_<plugin_name>
kong.plugins.<plugin_name>.migrations.001_<from-version>_to_<to_version>
kong.plugins.<plugin_name>.migrations.002_<from-version>_to_<to_version>
```

## [创建迁移文件夹](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#create-the-migrations-folder)

定义模型后，必须创建迁移模块，该模块将由Kong执行，以创建用于存储您的实体记录的表。

如果您的插件旨在同时支持Cassandra和Postgres，则必须编写两种迁移。

如果您的插件还没有插件，则应在其中添加一个`<plugin_name>/migrations` 文件夹。如果`init.lua`内部没有文件，则应创建一个。在此将引用您插件的所有迁移。

`migrations/init.lua`文件的初始版本将指向单个迁移。

在这种情况下，我们称之为`000_base_my_plugin`。

```
-- `migrations/init.lua`
return {
  "000_base_my_plugin",
}
```

这意味着将包含一个文件，`<plugin_name>/migrations/000_base_my_plugin.lua` 其中包含初始迁移。我们将在一分钟内看到如何完成此操作。

## [向现有插件添加新的迁移](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#adding-a-new-migration-to-an-existing-plugin)

有时，必须在插件版本发布后进行更改。可能需要新功能。数据库表行可能需要更改。

发生这种情况时，*您必须*创建一个新的迁移文件。你*千万不要*一经发布修改现有的迁移文件（你仍然可以让他们更强大和防弹如果你想，如总是尽量写迁移重入）。

虽然没有严格的规则来命名您的迁移文件，但是有一个约定，第一个以开头`000`，第二个以开头`001`，依此类推。

在前面的示例之后，如果我们要发布具有数据库更改的新版本插件（例如，需要一个名为的表`foo`），则可以通过添加一个名为的文件`<plugin_name>/migrations/001_100_to_110.lua`并将其引用到迁移初始化文件中来插入该插件。像这样（`100`该插件的先前版本在哪里，`1.0.0`以及 `110`该插件迁移到的版本`1.1.0`：

```
-- `<plugin_name>/migrations/init.lua`
return {
  "000_base_my_plugin",
  "001_100_to_110",
}
```

## [迁移文件语法](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#migration-file-syntax)

虽然Kong的核心迁移同时支持Postgres和Cassandra，但是自定义插件可以选择同时支持它们之一或仅支持其中之一。

迁移文件是一个Lua文件，它返回具有以下结构的表：

```
-- `<plugin_name>/migrations/000_base_my_plugin.lua`
return {
  postgresql = {
    up = [[
      CREATE TABLE IF NOT EXISTS "my_plugin_table" (
        "id"           UUID                         PRIMARY KEY,
        "created_at"   TIMESTAMP WITHOUT TIME ZONE,
        "col1"         TEXT
      );
    
      DO $$
      BEGIN
        CREATE INDEX IF NOT EXISTS "my_plugin_table_col1"
                                ON "my_plugin_table" ("col1");
      EXCEPTION WHEN UNDEFINED_COLUMN THEN
        -- Do nothing, accept existing state
      END$$;
    ]],
  },

  cassandra = {
    up = [[
      CREATE TABLE IF NOT EXISTS my_plugin_table (
        id          uuid PRIMARY KEY,
        created_at  timestamp,
        col1        text
      );
      
      CREATE INDEX IF NOT EXISTS ON my_plugin_table (col1);
    ]],
  }
}

-- `<plugin_name>/migrations/001_100_to_110.lua`
return {
  postgresql = {
    up = [[
      DO $$
      BEGIN
        ALTER TABLE IF EXISTS ONLY "my_plugin_table" ADD "cache_key" TEXT UNIQUE;
      EXCEPTION WHEN DUPLICATE_COLUMN THEN
        -- Do nothing, accept existing state
      END;
    $$;
    ]],
    teardown = function(connector, helpers)
      assert(connector:connect_migrations())
      assert(connector:query([[
        DO $$
        BEGIN
          ALTER TABLE IF EXISTS ONLY "my_plugin_table" DROP "col1";
        EXCEPTION WHEN UNDEFINED_COLUMN THEN
          -- Do nothing, accept existing state
        END$$;
      ]])
    end,
  },

  cassandra = {
    up = [[
      ALTER TABLE my_plugin_table ADD cache_key text;
      CREATE INDEX IF NOT EXISTS ON my_plugin_table (cache_key);
    ]],
    teardown = function(connector, helpers)
      assert(connector:connect_migrations())
      assert(connector:query("ALTER TABLE my_plugin_table DROP col1"))
    end,
  }
}
```

如果插件仅支持Postgres或Cassandra，则仅需要一种策略的部分。每个策略部分都有两个部分，`up`和`teardown`。

- `up`是原始SQL / CQL语句的可选字符串。这些语句将在执行时`kong migrations up`执行。
- `teardown`是一个可选的Lua函数，它带有一个`connector`参数。这样的连接器可以调用该`query`方法来执行SQL / CQL查询。拆解是由触发 `kong migrations finish`

建议在这些部分上完成所有非破坏性操作（例如创建新表和添加新记录）`up`，而在非破坏性操作（例如删除数据，更改行类型，插入新数据）上进行这些`teardown`部分。

在这两种情况下，建议都编写所有SQL / CQL语句，以便它们尽可能地可重入。`DROP TABLE IF EXISTS`代替`DROP TABLE`， `CREATE INDEX IF NOT EXIST`而不是`CREATE INDEX`等，如果迁移由于某种原因失败，预计在解决了这个问题的第一次尝试将简单地重新运行迁移。

尽管Postgres支持，但Cassandra不支持诸如“ NOT NULL”，“ UNIQUE”或“ FOREIGN KEY”之类的约束，但是Kong在定义模型的模式时为您提供了这些功能。请记住，该架构对于Postgres和Cassandra都是相同的，因此，您可能会为使用Cassandra的架构权衡纯SQL架构。

**重要说明**：如果`schema`使用`unique`约束，则Kong将为Cassandra实施约束，但对于Postgres，必须在迁移中设置此约束。

要查看实际示例，请看一下[Key-Auth插件的迁移](https://github.com/Kong/kong/tree/1.3.x/kong/plugins/key-auth/migrations)。

## [定义架构](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#defining-a-schema)

在自定义插件中使用自定义实体的第一步是定义一个或多个*模式*。

模式是描述实体的Lua表。这里有结构信息，例如如何命名实体的不同字段以及它们的类型是什么，类似于描述[插件配置](https://docs.konghq.com/1.3.x/plugin-development/plugin-configuration/)的字段。与插件配置架构相比，自定义实体架构需要其他元数据（例如，哪个或哪些字段构成实体的主键）。

模式将在名为以下模块的模块中定义：

```
kong.plugins.<plugin_name>.daos
```

意味着`<plugin_name>/daos.lua`在您的插件文件夹中应该有一个名为的文件。该`daos.lua`文件应返回一个包含一个或多个模式的表。例如：

```
-- daos.lua
local typedefs = require "kong.db.schema.typedefs"


return {
  -- this plugin only results in one custom DAO, named `keyauth_credentials`:
  keyauth_credentials = {
    name                  = "keyauth_credentials", -- the actual table in the database
    endpoint_key          = "key",
    primary_key           = { "id" },
    cache_key             = { "key" },
    generate_admin_api    = true,
    admin_api_name        = "key-auths",
    admin_api_nested_name = "key-auth",    
    fields = {
      {
        -- a value to be inserted by the DAO itself
        -- (think of serial id and the uniqueness of such required here)
        id = typedefs.uuid,
      },
      {
        -- also interted by the DAO itself
        created_at = typedefs.auto_timestamp_s,
      },
      {
        -- a foreign key to a consumer's id
        consumer = {
          type      = "foreign",
          reference = "consumers",
          default   = ngx.null,
          on_delete = "cascade",
        },
      },
      {
        -- a unique API key
        key = {
          type      = "string",
          required  = false,
          unique    = true,
          auto      = true,
        },
      },
    },
  },
}
```

此示例`daos.lua`文件引入了一个名为的架构`keyauth_credentials`。

这是一些顶级属性的描述：

| 名称                    | 类型                | 描述                                                         |
| ----------------------- | ------------------- | ------------------------------------------------------------ |
| `name`                  | `string`（需要）    | 它将用于确定DAO名称（`kong.db.[name]`）。                    |
| `primary_key`           | `table`（需要）     | 构成实体主键的字段名称。即使大多数Kong核心实体当前使用名为的UUID，架构也支持复合键 `id`。如果您使用的是Cassandra，并且需要组合键，则它应该与分区键具有相同的字段。 |
| `endpoint_key`          | `string`（可选的）  | 用作Admin API上备用标识符的字段名称。在上面的示例中，`key`是endpoint_key。这意味着具有`id = 123`和的凭证 `key = "foo"`可以同时称为 `/keyauth_credentials/123`和`/keyauth_credentials/foo`。 |
| `cache_key`             | `table`（可选的）   | 包含用于生成的字段名称`cache_key`，该字符串必须明确标识Kong缓存中的实体。像`key`您的示例一样，唯一字段通常是不错的选择。在其他情况下，最好是几个字段的组合。 |
| `generate_admin_api`    | `boolean`（可选的） | 是否自动为实体生成管理api。默认情况下，会为所有dao（包括自定义dao）生成admin api。如果要为dao创建完全定制的管理api或完全禁用dao的自动生成，请将此选项设置为`false`。 |
| `admin_api_name`        | `boolean`（可选的） | 当`generate_admin_api`启用了管理API自动生成器使用`name` 导出收藏网址，自动生成的管理API。有时，您可能想使用不同于的名称来命名集合网址`name`。例如，使用DAO，`keyauth_credentials` 我们实际上希望自动生成器为此dao生成端点，并使用其他更友好的网址名称`key-auths`（例如`http://<KONG_ADMIN>/key-auths`代替`http://<KONG_ADMIN>/keyauth_credentials`）。 |
| `admin_api_nested_name` | `boolean`（可选的） | 类似`admin_api_name`的`admin_api_nested_name`一个DAO的名称管理API自动生成嵌套上下文创建指定。如果您对`name`或不满意，则只需要使用此参数`admin_api_name`。由于遗留的原因，Kong的URL像`http://<KONG_ADMIN>/consumers/john/key-auth`哪里`key-auth` 没有遵循复数形式`http://<KONG_ADMIN>/key-auths`。`admin_api_nested_name`在这种情况下，您可以指定其他名称。 |
| `fields`                | `table`             | 每个字段定义都是一个带有单个键的表，该键是该字段的名称。表值是包含字段*属性*的子表，下面将解释其中的一些*属性*。 |

许多字段属性编码*验证规则*。尝试使用DAO插入或更新实体时，将检查这些验证，如果提供的输入不符合它们，则会返回错误。

的`typedefs`变量（通过要求获得`kong.db.schema.typedefs`）是含有很多有用的类型定义和别名，包括一个表`typedefs.uuid`，最常用的类型的主键，并且`typedefs.auto_timestamp_s`，对于`created_at`字段。在定义字段时广泛使用它。

这是对某些可用字段属性的非详尽解释：

| 属性名称    | 类型                      | 描述                                                         |
| ----------- | ------------------------- | ------------------------------------------------------------ |
| `type`      | `string`                  | 架构支持以下标量类型：`"string"`，`"integer"`，`"number"`和`"boolean"`。还支持诸如`"array"`，`"record"`或的复合类型`"set"`。  除了这些值之外，该`type`属性还可以采用特殊`"foreign"`值，该特殊值表示外部关系。  每个字段都需要由通过迁移创建的适当相似类型的数据库字段支持。  `type`是所有字段定义的唯一必需属性。 |
| `default`   | `any`（与`type`属性匹配） | 如果未提供值，则指定尝试插入字段时该字段将具有的值。默认值始终通过Lua设置，而不是通过基础数据库设置。因此，建议不要在迁移中的字段上设置任何默认值。 |
| `required`  | `boolean`                 | 当设置为`true`on字段时，尝试插入缺少该字段值的实体时将抛出错误（除非所讨论的字段具有默认值）。 |
| `unique`    | `boolean`                 | 当`true`在字段上设置为时，尝试在数据库上插入实体时将引发错误，但另一个实体在所述字段上已经具有给定值。在使用PostgreSQL时，*必须*通过`UNIQUE`在迁移中声明字段来备份此属性。Cassandra策略会在尝试插入之前在Lua中进行检查，因此不需要任何特殊处理。 |
| `auto`      | `boolean`                 | 当尝试插入实体而不为此提供值时，将字段`auto`设置为`true`，   如果为`type == "uuid"`，则该字段将采用随机UUID作为值。如果为`type == "string"`，则该字段将采用随机字符串。如果字段名称为`created_at`或`updated_at`，则该字段将在适当时插入/更新时使用当前时间。 |
| `reference` | `string`                  | 类型的字段必填`foreign`。给定的字符串*必须*是现有架构的名称，外键将“指向”该架构。这意味着，如果模式B具有指向模式A的外键，则需要在B之前加载A。 |
| `on_delete` | `string`                  | 对于类型的字段是可选的和排他的`foreign`。它指示在删除引用的实体时，通过外键链接的实体必须发生的情况。它可以具有三个可能的值：  `"cascade"`：删除链接的实体时，还必须删除所有从属实体。`"null"`：删除链接的实体时，所有从属实体的外键字段都将设置为`null`。`"restrict"`：尝试删除具有链接实体的实体将导致错误。  在Cassandra中，这是用纯Lua代码处理的，但是在PostgreSQL中，有必要像`ON DELETE CASCADE/NULL/RESTRICT`在迁移中一样声明引用。 |

要了解有关模式的更多信息，请参阅：

- [typedefs.lua](https://github.com/Kong/kong/blob/1.3.0/kong/db/schema/typedefs.lua)的源代码 可以了解默认情况下提供的内容。
- [核心架构，](https://github.com/Kong/kong/tree/1.3.0/kong/db/schema/entities) 以查看此处未讨论的其他一些字段属性的示例。
- [`daos.lua`](https://github.com/search?utf8=%E2%9C%93&q=repo%3Akong%2Fkong+path%3A%2Fkong%2Fplugins+filename%3Adaos.lua)本指南[以嵌入式插件的](https://github.com/search?utf8=%E2%9C%93&q=repo%3Akong%2Fkong+path%3A%2Fkong%2Fplugins+filename%3Adaos.lua)[所有](https://github.com/search?utf8=%E2%9C%93&q=repo%3Akong%2Fkong+path%3A%2Fkong%2Fplugins+filename%3Adaos.lua)[文件](https://github.com/search?utf8=%E2%9C%93&q=repo%3Akong%2Fkong+path%3A%2Fkong%2Fplugins+filename%3Adaos.lua)（尤其[是key-auth ](https://github.com/Kong/kong/blob/1.3.0/kong/plugins/key-auth/daos.lua)[文件）](https://github.com/search?utf8=%E2%9C%93&q=repo%3Akong%2Fkong+path%3A%2Fkong%2Fplugins+filename%3Adaos.lua)为例。

## [定制的DAO](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#the-custom-dao)

模式不直接用于与数据库交互。而是为每个有效模式构建一个DAO。DAO采用其包装的模式的名称，并且可以通过`kong.db`接口访问。

对于上面的示例架构，生成的DAO可通过来用于插件`kong.db.keyauth_credentials`。

### [选择一个实体](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#selecting-an-entity)

```
local entity, err, err_t = kong.db.<name>:select(primary_key)
```

尝试在数据库中找到一个实体并将其返回。可能发生三件事：

- 已找到实体。在这种情况下，它作为常规Lua表返回。
- 发生错误-例如与数据库的连接丢失。在这种情况下，第一个返回值将是`nil`，第二个返回值将是描述错误的字符串，而最后一个将是表形式的相同错误。
- 不会发生错误，但是找不到实体。然后，该函数将仅返回`nil`，而不会出现错误。

用法示例：

```
local entity, err = kong.db.keyauth_credentials:select({
  id = "c77c50d2-5947-4904-9f37-fa36182a71a9"
})

if err then
  kong.log.err("Error when inserting keyauth credential: " .. err)
  return nil
end

if not entity then
  kong.log.err("Could not find credential.")
  return nil
end
```

### [遍历所有实体](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#iterating-over-all-the-entities)

```
for entity, err on kong.db.<name>:each(entities_per_page) do
  if err then
    ...
  end
  ...
end
```

该方法通过发出分页的请求，有效地遍历数据库中的所有实体。该`entities_per_page`参数默认为`100`，控制每页返回多少个实体。

在每次迭代中，`entity`将返回一个新值，或者，如果有任何错误，则该`err` 变量将填充一个错误。推荐的迭代方法是`err`先检查，否则假定`entity`存在。

用法示例：

```
for credential, err on kong.db.keyauth_credentials:each(1000) do
  if err then
    kong.log.err("Error when iterating over keyauth credentials: " .. err)
    return nil
  end

  kong.log("id: " .. credential.id)
end
```

此示例遍历1000个项目的页面中的凭据，并记录其ID，除非发生错误。

### [插入实体](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#inserting-an-entity)

```
local entity, err, err_t = kong.db.<name>:insert(<values>)
```

在数据库中插入一个实体，并返回所插入实体的副本或 `nil`，错误消息（字符串）和以表格形式描述错误的表格。

插入成功后，返回的实体将包含`default`和产生的额外值 `auto`。

下面的示例使用`keyauth_credentials`DAO为给定的使用者插入证书，并将其设置`key`为`"secret"`。注意引用外键的语法。

```
local entity, err = kong.db.keyauth_credentials:insert({
  consumer = { id = "c77c50d2-5947-4904-9f37-fa36182a71a9" },
  key = "secret",
})

if not entity then
  kong.log.err("Error when inserting keyauth credential: " .. err)
  return nil
end
```

假设未发生错误，则返回的实体将`auto`填充字段，如`id`和`created_at`。

### [更新实体](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#updating-an-entity)

```
local entity, err, err_t = kong.db.<name>:update(primary_key, <values>)
```

更新现有实体，只要可以使用提供的主键和一组值找到它即可。

返回的实体将是更新发生后的实体，或`nil`+错误消息+错误表。

以下示例在`key`给定凭据ID 的情况下修改了现有凭据的字段：

```
local entity, err = kong.db.keyauth_credentials:update({
  { id = "2b6a2022-770a-49df-874d-11e2bf2634f5" },
  { key = "updated_secret" },
})

if not entity then
  kong.log.err("Error when updating keyauth credential: " .. err)
  return nil
end
```

请注意，用于指定主键的语法与用于指定外键的语法相似。

### [升级实体](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#upserting-an-entity)

```
local entity, err, err_t = kong.db.<name>:upsert(primary_key, <values>)
```

`upsert`是的混合物`insert`和`update`：

- 当提供的内容`primary_key`标识现有实体时，其工作方式类似于`update`。
- 当提供的内容`primary_key`无法识别现有实体时，其工作方式类似于`insert`

给出以下代码：

```
local entity, err = kong.db.keyauth_credentials:upsert({
  { id = "2b6a2022-770a-49df-874d-11e2bf2634f5" },
  { consumer = { id = "a96145fb-d71e-4c88-8a5a-2c8b1947534c" } },
})

if not entity then
  kong.log.err("Error when upserting keyauth credential: " .. err)
  return nil
end
```

可能发生两件事：

- 如果`2b6a2022-770a-49df-874d-11e2bf2634f5`存在ID为id的凭据，则此代码将尝试将其Consumer设置为所提供的。
- 如果凭据不存在，则此代码将尝试使用给定的id和Consumer创建一个新的凭据。

### [删除实体](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#deleting-an-entity)

```
local ok, err, err_t = kong.db.<name>:delete(primary_key)
```

尝试删除由标识的实体`primary_key`。调用此方法后，`true` 如果该实体*不存在*，则返回；如果`nil`检测到错误，则返回+错误+错误表。

请注意，`delete`如果*在调用*实体之前不存在该实体，则调用将成功。这是出于性能方面的考虑-如果可以避免，我们希望避免执行先删除后读取。如果您要进行此检查，则必须手动进行检查，方法是`select`在调用之前进行检查`delete`。

例：

```
local ok, err = kong.db.keyauth_credentials:delete({
  { id = "2b6a2022-770a-49df-874d-11e2bf2634f5" }
})

if not ok then
  kong.log.err("Error when deleting keyauth credential: " .. err)
  return nil
end
```

## [缓存自定义实体](https://docs.konghq.com/1.3.x/plugin-development/custom-entities/#caching-custom-entities)

有时，每个请求/响应都需要自定义实体，这反过来每次都会触发对数据存储区的查询。这是非常低效的，因为查询数据存储会增加延迟并减慢请求/响应的速度，并且由此导致的数据存储负载增加可能会影响数据存储本身以及其他Kong节点的性能。

当在每个请求/响应上都需要自定义实体时，优良作法是利用Kong提供的内存中缓存API将其缓存在内存中。

下一章将重点介绍缓存自定义实体，并在数据存储中更改它们时使它们无效：[缓存自定义实体](https://docs.konghq.com/1.3.x/plugin-development/entities-cache/)。
